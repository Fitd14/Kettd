## 2. Why Now（为什么是现在，四条实测证据）

1. **现在能打出去的安装包是过期的。** `target/release/待办列表.exe` = 21:00:47，msi/nsis 打包 = 21:03；而发版前 8 项调整的源码改在 21:34–21:46、`runtime.rs` 改在 22:11。**当前 2.0.0 安装物不含那 8 项调整。**
2. **那 8 项调整一行都没提交。** `git status`：15 个文件 modified 未提交；`git show HEAD:src/float.html` 里标题仍是「悬浮面板 · 待办列表」、按钮仍是文字「记下」，工作区才是新标题 + 图标按钮。且 **`v2` 分支没有 upstream**（origin 只有 master/v1）→ 源码只活在 F 盘这一台机器上，工作区一旦被覆盖就没有回滚点。
3. **契约文档已经在说谎。** `V2-API.md` §10 写着「未做 cargo check / 本沙箱无 webkit2gtk」，但本机实测 `cargo check` **0.95s 通过**（缓存命中、只有 7 条 dead-code warning），cargo 1.96.1 + WebView2(Edge 152) 齐活。过期声明会把下一次会话（含我）的推断带偏。
4. **验证窗口只有这台机器，而且它正在被真实使用。** 真库 `%APPDATA%/todo-list/data.json`：17 条任务里 **16 条 source=capture**、13 条带 `doneAt`、5 条软删、`fired` 里有 4 条 `t|…|2026-09-03` 去重键 —— 捕获与提醒去重链路真的在跑。但 `reminders: 0` → 计划页提醒路径事实上从未被真实使用过，这个盲点只有现在点一遍能补上。

## 4. Direction & Alternatives

### 押：A — 发版收口（重打包 → 运行时验证 → 数据保护 → 可证伪契约）

- **用户价值**：那 8 项精简调整只有装进包、被别人装到机器上，才对别人存在。
- **业务价值**：brief 的硬约束「v1 数据一次性兼容迁移零丢失」目前**既没被证实也没被证伪**；收口是把它变成可证伪的唯一路径。

### 考虑过但不押（诚实的 trade-off）

- **B 度量埋点 + 周汇总假设验证**（retro 判定的 5 星零证据假设 B4）→ 价值最高，但不产出可交付版本，且本地单机埋点**得先设计统计口径**才有意义；推到 v2.2 的第一交付。
- **C 补 Wave-3（周汇总 / 打字即搜）**→ **实测这条是伪需求**：周汇总草稿 tab 在 `src/index.html:718-780`、打字即搜浮层在 `1103-1149`、`api.js:62 export_weekly` 已在生产层。没有 Wave-3 可补。
- **D 体验/动效打磨** → QA 9 个维度里 7 个无 deviation，此刻收益远低于换掉过期安装包。

### 我们最不确定的事

**关键假设**：「这版只要重打包 + 真机点一遍就达到可发版」。
**证伪条件**：T2 运行时验证里那两项静态无法证伪的（capture 窗透明观感、Alt+Shift+O 实际呼出）如果真不出效果 → 一周窗口不够。
**止损**：把 T2 排在第 1 天做；暴露 Blocker 就当场砍掉 Should 层（T8/T9/T10），Must 层不动。

## 5. Design Decisions（5 个，含证据与判据）

### 决策 1：先钉基线、再换发布物、最后才改代码（顺序本身是决策）
**为什么**：任何「改了没生效」的体感，在包里是 21:00 旧产物时都不可归因。
**证据**：bundle 21:03 vs 源码 21:34–22:11；`git show HEAD:src/float.html` ≠ 工作区；`v2` 无 upstream。
**判据**：`git log -1` 含 8 项调整 + `git ls-remote origin v2` 有 ref + 新包 mtime > 全部源码 mtime。
**待确认**：`runtime.rs` 改于 22:11:35、debug exe 建于 22:11:41，只差 6 秒，不足以完成一次重编 → 不能断言当前运行的二进制含最后一次编辑，需重跑 build 确认同代。

### 决策 2：4 项 QA 偏差里只有 qa-3 会改数据，所以它排最前
**为什么**：`index.html:654-673` 的 `rem-edit` 对 `HH:MM/HH:MM` 走 else 分支把日期与时刻**双双置空**，`:674` 保存即覆盖为单值 —— 这是静默改写用户旧数据，违反 brief 约束 #2 与 V2-API §时间约定，不是文案问题。
**判据**：多时刻行进入编辑 → 不改值直接保存 → 落库值仍为 `HH:MM/HH:MM`；或改前先显式确认。

### 决策 3：迁移与时间契约用单测证明，不用手点
**为什么**：全仓 `#[test]` 计数 = 0；`store.rs:34 data_dir()` 把目录硬编码成 `%APPDATA%/todo-list`，手点回归必然污染真库（也就会毁掉唯一的 dogfood 样本）。而 `store.rs:447 migrate_v1(&Value)`、`models.rs:596/626/674/684` 全是纯函数，天生可测。
**判据**：`cargo test` ≥5 例绿，覆盖 V2-API §7 十规则里的抽样（空格制式、多时刻原样保留、「个人」→「生活」、`medium`→`med`、解析失败置 `null` 并进 issues）。
**顺带的使能项**：加一个 `KETTD_DATA_DIR` 环境变量覆盖（≤30 行）——它不是功能，是「能安全回归」的前提；不做则第二实例与迁移回归两条路都堵死。

### 决策 4：热键失败必须可见（同一类资源不能两种处理）
**为什么**：`main.rs:101-108` 捕获热键重试 4 次，`:110` 主界面热键 `let _ =` 直接丢弃结果 → 设置页显示的「当前绑定」可能是没绑上的。违反 brief「控件皆有实行为」。
**判据**：占用冲突时设置页标「未生效」+ 托盘提示一次；只有真注册成功才写「当前绑定」。

### 决策 5：文档纠偏与代码同批提交，并把对比度 open 项关掉
**为什么**：V2-API §10 的过期声明比 bug 更贵（误导后续会话）。另外 check-5「muted 4.4–4.6:1 临界」这项 open，本轮按 token 实算：亮色 `muted/bg 4.68:1`、`muted/card 4.86:1`，暗色 `6.36:1`、`5.87:1` → **全部 ≥4.5:1，AA 通过**，可关（口径是 token 计算值，不是截图取样）。
**判据**：§10 改写为真机结论 + 剩余未验清单；check.json 标 closed。

## 6. Asks（需要你拍板，4 元字段齐全）

### Ask 1：计划页时间语义保留哪种？
- **为什么需要决定**：`qa-4` 的范围增益（日期留空=每天循环 / 选日期=一次性）还没被需求方确认；而 qa-3 的「多时刻」修复口径取决于多时刻归在哪一类，不定就没法冻结。
- **决定时间**：2026-09-04（周五）前
- **如果不决定**：T3 修法定不下来 → 发版包无法冻结，T1/T10 全部顺延。
- **选项**：A 保留双组件 + 行内加一句语义说明（推荐，最小改动）· B 只留纯时刻、删日期组件（放弃一次性提醒入口）· C 拆成显式「每天 / 单次」开关

### Ask 2：运行时验证要不要重启你正在跑的实例（PID 12196）？
- **为什么需要决定**：T2 四项里两项必须真机看点。当前实例是 debug 构建，且 `runtime.rs` 与它的 6 秒时间差不能确认同代。
- **决定时间**：现在（T2 的前置）
- **如果不决定**：收口只剩代码层，「装得出去」这条不成立。
- **选项**：A 允许直接重启现有实例 · B 先加 `KETTD_DATA_DIR` 用独立数据目录起第二实例（推荐，多 30 分钟，不打断 dogfood 也不脏真库）· C 今天不验证

### Ask 3：v1 迁移回归用哪个数据源？
- **为什么需要决定**：`%APPDATA%/todo-list` 里没有 `data.v1.json`（真库已是 v2 态），意味着「零丢失」这条硬约束目前无处验证。
- **决定时间**：2026-09-04 前
- **如果不决定**：要么接受「存量数据丢失率 0」不可证（并在发版说明里写风险声明），要么 T6 的迁移单测没有 fixture 方向。
- **选项**：A 你有 v1 的 `data.json` → 给我路径 · B 没有 → 我按 V2-API §7 十规则手写 fixture 做单测（推荐）· C 不做，发版说明标未验证

### Ask 4：发布物与版本号：msi + nsis 双出还是单出？v2.1.0 还是 2.0.1？
- **为什么需要决定**：当前 `target/release/bundle/` 同时躺着 `待办列表_2.0.0_x64.msi` 与 `-setup.exe`，两份过期产物都是可分发来源 → 只要留着装错就是「改了没生效」。
- **决定时间**：2026-09-05 前
- **如果不决定**：最后一天还在纠结打包，且过期包有被误装风险。
- **推荐**：只留 nsis + 版本号 `2.1.0`（8 项调整 + qa-1/2/3 修复是功能级变更，不是补丁）+ 删除旧 bundle 目录产物。

### Ask 5：同意把「度量埋点 + 周汇总刚需验证」明确推到 v2.2？
- **为什么需要决定**：这是 retro 认定的最大单点风险（5 星假设零证据、PRD 5 个成功指标目前全不可测），但它与「发版收口」抢同一周窗口。
- **决定时间**：2026-09-04 前
- **如果不决定**：一周窗口会被功能扩展吃掉，v2.1 与 v2.2 同时半途而废。
- **选项**：A 同意推 v2.2（推荐）· B v2.1 里先做埋点最小集（则 Must 层砍 T8/T9/T10 换工时）

> **rev.1 的 4 个 Asks 处置**（本轮顺带核账）：Ask2「推 v2 分支到远端」**仍未拍板且仍未执行**（`v2` 无 upstream）→ 升级为本轮 Ask；Ask1/Ask3/Ask4 属 Beta 期议题，v2.1 不阻塞，原样挂账。
