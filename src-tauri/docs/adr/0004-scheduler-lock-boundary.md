# ADR-0004: 调度器 tick 的锁边界重排

**状态**：Proposed（优先级最高，且排在 M1 之前）
**日期**：2026-09-05
**关联**：`ARCHITECTURE-v3.md` §6/§8-R3 · ADR-002（Clock 端口）

## Context

`scheduler.rs` 的 1s tick 在**持有全局 `Mutex<Store>` 守卫的整个期间**做完了所有事：

```rust
scheduler.rs:68   let mut store = slot.lock()      ← 取锁
              :70   tick(&app, &mut store, &mut state)
              :132     runtime::notify(...)        ← OS 通知（跨进程 IPC）
              :165     runtime::notify(...)        ← OS 通知
              :185     runtime::notify(...)        ← OS 通知
              :227     store.save()                ← 磁盘：轮转 5 份备份 + 序列化 + rename
              :74   drop(store)                    ← 到这里才放锁
```

也就是说：**每一次有提醒到点，全应用的 40 个命令都要排队等「OS 通知调用 + 磁盘写」完成。**

这不是理论风险：`save()` 会做 `rotate_backups()`（把 `data.json.bak-1..5` 逐个顺移，5 次文件操作）+ 全量序列化 + `fs::rename`。在机械盘或杀毒软件介入时，这几十毫秒到几百毫秒全部落在锁临界区内。而 UI 侧每个写命令（勾选完成、加子任务、改备注）都要同一把锁。

叠加两个 v3 趋势会让它更糟：
- **多张便签窗口**（ADR-007）意味着更多窗口各自轮询/写入；
- 现在还有一个 `float.html:169` 的 **30s 心跳** 周期性去抢锁重拉数据。

## Decision Drivers

- 必须：锁临界区内不得出现 OS 调用与磁盘 IO。
- 必须：保持「不重复提醒」承诺 —— fired 去重键的读写不能因为重排而出现竞态（否则重启后轰炸，这是 v1 的老病）。
- 必须：改动局限在 `scheduler.rs` 一个文件，可独立发布、可回滚。
- 应该：重排后的到期判定逻辑必须可测（依赖 ADR-002 的 `Clock`）。

## Considered Options

### A. 三段式：短锁快照 → 无锁计算 → 短锁写回 → 锁外通知（推荐）

```
① 拿锁 → clone(提醒列表, 任务提醒字段, settings, now) → 放锁
② 无锁：算到期集合、稳定键去重、DND 判定、每小时上限排队   ← 纯函数，可测
③ 拿锁 → 写回（fired 键 / completed / last_fired）→ save() → 放锁
④ 锁外：notify() + emit(store-changed / fired / missed)
```

- **优**：临界区从「通知 + 5 次备份轮转 + 序列化 + rename」缩到「clone」和「改 + save」两段，且**通知彻底移出**；②是纯函数，第一次可测。
- **劣**：①与③之间数据可能已被 UI 改动（TOCTTOU）。需要缓解，见风险。

### B. 通知异步化：tick 只投递到队列，另一个线程发

- **优**：改动更小。
- **劣**：磁盘写仍在锁内；且引入第二个线程与队列，复杂度换得不干净。

### C. 换 `RwLock`

- **劣**：不解决持锁做 IO 的问题（写者仍需独占锁），只是让读命令少排队。治不了病根。

### D. 把 `Store` 改成 actor（消息传递）

- **劣**：对单人项目是过度设计，且要重写 40 个命令的取数方式。

## Decision

采用 **A（三段式）**，并对 TOCTOU 采用**写回时重校验**：

③ 拿锁后，对每个待落地的到期项做一次**幂等前置检查** —— 若该稳定键已在 `fired` 中、或该提醒已被 UI 侧改成 disabled/completed、或 `snoozedUntil` 已被用户改期，则**跳过该项的写与通知**。通知（④）只在③确认"这次真的是我触发的"之后才发。

这保证：即使 ①–③ 之间用户改了数据，也不会出现"已停用的提醒仍然响"或"重复响"。

## Consequences

**正面**
- 到点提醒不再阻塞 UI 写命令；便签窗口变多后仍然成立。
- 到期判定成为纯函数 → 与 ADR-002 的 `FixedClock` 配合，第一次可以测 DND 跨午夜、每周重复、错过 24h 降级、每小时上限排队这四类边界。
- 通知失败（`notify()` 返回 false）不再持有锁，不会连带卡住写盘。

**负面**
- ①的 clone 有内存开销（提醒列表 + 任务提醒字段）。单用户数据量下可忽略，但要如实记录。
- 代码从"一把锁走到底"变成三段，读起来需要理解幂等重校验的必要性 —— 必须在函数上写明，否则后人会"顺手简化"回一把锁。

**风险与缓解**
- 风险：幂等重校验漏了一种状态（例如只查 fired 没查 snoozedUntil）→ 重复响。缓解：把重校验条件写成**一个函数**并在其单测里穷举四种"①之后被改"的情况。
- 风险：`save()` 仍在③的锁内（磁盘 IO 未移出）。缓解：**本期有意保留** —— 写盘必须在锁内才能保证原子读改写；移出锁会引入并发写风险，收益也不大（磁盘写远快于 OS 通知）。这一点在代码注释里写明，避免被误读为"没做完"。

## Implementation Notes

1. 依赖顺序：ADR-002 的 `Clock` 先就位（否则②无法测）。但**锁重排本身不依赖测试也能做**，所以本 ADR 允许先做重排、后补测试。
2. 落点：M0.5（在 ADR-0001 的 M1 之前），已拍板顺序为「0006 内核抽模块 → 0004 调度锁 → M1」。
3. 出口判据：① 通知调用不在任何持锁作用域内（可用 grep + 人工复核）；② 到点仍响且不重复（真机复验，沿用 V2-API §10 已有的截图基线）；③ ②段纯函数有表驱动测试。
4. 回滚：单文件改动，`git revert` 即可。
